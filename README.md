# 請求書 → 弥生会計 仕訳インポートCSV

請求書の写真から、会計ソフト（弥生会計）にそのまま取り込める仕訳CSVを作ります。

多くのOCR活用は「読み取ってJSONにする」で止まりますが、経理の現場で手が止まるのは
その先です。このデモは、読み取った値を**仕訳として並ぶところまで**持っていきます。

---

## 使い方

```bash
export SPACE_OCR_API_KEY='spocr_...'
python main.py invoices/*.jpg -o out/
```

出力：

| ファイル | 内容 |
|---|---|
| `out/shiwake.csv` | 弥生インポート形式（27列・CP932）。そのまま取り込めます |
| `out/kakunin.csv` | 人が確認すべき箇所の一覧 |
| `out/raw/*.json` | APIの生レスポンス |

弥生会計 Next への取り込みは `設定` → `インポート・エクスポート` から。

---

## 何をしているか

### 1. 抽出スキーマ（schema.py）

`POST /ocr/fields` に渡すスキーマで、次の4つを使い分けています。

**`pattern` で形式を宣言する**

登録番号に `^T\d{13}$` を宣言しています。適格請求書発行事業者の登録番号は
T＋数字13桁と決まっているので、`TO000000000002`（2文字目がO）のような誤読は、
文字照合の一致率を見るまでもなく `pattern_mismatch` として落ちます。

**`type: "date"` で日付として解釈できるか見る**

`2026年8月15일` のように字形の似た別文字が混ざった場合、日付としてパースできず
`type_mismatch` になります。一致率0.90という微妙な値に依存しません。

**`review: "off"` で自由記述の列を静かにする**

品名・単位・備考には `review: "off"` を付けています。品名が「WF」でも「VVF」でも
仕訳は同じように切れます（摘要欄に入る情報なので実害がない）。ここで要確認を出すと、
登録番号や税額に立った印が埋もれます。

**`label` で座標を安定させる**

合計金額は書面の上下2か所に同じ数字が印字されることが多いため、
`label: ["ご請求金額", "合計"]` を添えています。

### 2. 仕訳の組み立て（journal.py）

**税率ごとに分けて切る**

合計が合っていても税率区分を混ぜると申告額がずれます。明細を
（勘定科目 × 税率）で束ね、8%と10%を別々の仕訳にしています。

**税抜／税込を判定して税込に直す**

日本のBtoB請求書は税抜表示が多い一方、弥生の「課対仕入込」は税込入力です。
明細合計が対象額と一致すれば税抜、請求合計と一致すれば税込と判定し、
税抜の場合は宣言された消費税額を金額比で按分して税込に直します。
端数は最大のグループに寄せ、仕訳の合計が請求額と必ず一致するようにしています。

**勘定科目は当てずっぽうで埋めない**

品名から判定できなかった行は `仮払金` に置き、要確認として出します。
それらしい科目を推測で入れる方が、後から見つけにくくなります。

### 3. 人が確認すべき箇所（kakunin.csv）

2段階に分けています。

| 区分 | 意味 |
|---|---|
| `error` | 値が誤っている可能性が高い。取り込む前に直すべきもの |
| `warn` | 判定できなかった。取り込んでから直せるもの |

APIが返す `review.flagged` のうち、呼び出し側が宣言したルール違反
（`pattern_mismatch` / `type_mismatch` / `missing`）は `error`、
エンジンの推定（`text_mismatch` / `low_ratio` など）は `warn` にしています。
前者は自分で書いた規則が破られたということなので、根拠が強いためです。

これに加えて、こちら側で次の検算を行っています。

- **数量 × 単価 = 金額**（明細行ごと）
- 対象額 + 消費税 = 合計
- 税率ごとの明細合計 = 対象額
- 作成した仕訳の合計 = 請求合計

要確認がある請求書は、摘要の先頭に `【要確認】` を付けて出力します。
弥生に取り込んだ後も仕訳日記帳の画面上で見分けられます。

### 4. 読み取り結果を保存する

`out/raw/*.json` に生レスポンスを保存し、2回目以降は再利用します。
経理は同じ書類を月次・決算・調査時と複数回見るため、そのたびに値が変わると
前回の処理と突合できません。確定値として扱えるようにしています。

## 現時点の制約

- **非適格請求書の税区分**に対応していません。登録番号がない、または形式が
  不正な請求書は要確認として出しますが、経過措置の税区分は付けていません。
  弥生側の区分名を確認したうえで対応する必要があります。
- **勘定科目の判定はキーワード方式**です。電気工事業で出てくる品目を前提に
  しているので、他業種ではルールの入れ替えが要ります。
- **2ページにまたがる請求書**は、ページごとに別の請求書として処理されます。
- APIキーは環境変数から読みます。ソースコードには含めていません。
